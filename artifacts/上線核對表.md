# 正式上線核對表

這份表給教授本人操作。現在不要合併 Pull Request，也不要更換 GitHub Pages。正式 Apps Script 還沒換之前，新畫面會接到舊後端。

成功與否只看下面寫的執行記錄或 JSON。任何一步失敗就停在那一步，用該步的回復方式，不要繼續下一步。

這次不要做：

- 不要執行 `sendReminders`、`previewRemindersToAdmin`、`pushGroupReminder`
- 不要把 `GROUP_PUSH_ENABLED` 設成 `true`
- 不要設定 `REPAIR_CONFIRM`，不要轉移陳永傑的綁定
- 不要把名單、userId、試算表 ID、權杖貼到 GitHub 或聊天

## 0. 先確認這份程式

後端版本是 `2026-11-release-2`。瀏覽器打開正式 `/exec` 之後，JSON 必須出現這個 `apiVersion`，才算後端就緒。

## 1. 舊程式還在時，先寫指令碼屬性

在 Apps Script「專案設定 → 指令碼屬性」。值從目前還沒換掉的舊程式複製，不要從 Git 找。

必填：

| 屬性 | 怎麼填 |
| --- | --- |
| `SHEET_ID` | 舊程式裡的試算表 ID |
| `SAINTS` | 舊程式六位聖徒，逗號分隔，一字不改 |
| `ADMIN_SAINT` | 舊程式的管理者姓名，必須是上面其中一位 |
| `ADMIN_USER_ID` | 舊程式的管理者 LINE userId |
| `JOSEPH_TOKEN` | 沿用已經存在的那一筆，不要重新貼到檔案 |

可省略：`LOGIN_CHANNEL_ID`。程式內定是 `2012397222`。

這時先不要填 `GROUP_PUSH_ENABLED`。遷移用的 `SOURCE_26_SHEET_ID`、`SOURCE_27_SHEET_ID` 留到第 6 步。

成功：五個必填屬性都有值，而且沒有出現在這個儲存庫。

出錯：少一個的話，第 4 步的 `releaseReadiness` 會列出缺少的屬性名稱，不會列出值。補上之後再繼續。

## 2. 備份

1. 試算表「檔案 → 建立複本」，檔名加上今天日期。
2. 再下載一份試算表，存到非公開的雲端硬碟。
3. 把目前 Apps Script 的 `Code.gs` 整份另存成 `Code.gs.舊版`。
4. 若 GitHub Pages 的 `index.html` 是你能下載的，也另存一份 `index.html.舊版`。

成功：你手上有試算表複本、下載檔、舊後端、舊前端。

出錯：還沒有這四份就不要貼新程式。這一步不改線上系統。

## 3. 貼上新後端並暫停舊觸發

1. 用這次交付的 `Code.gs` 整份取代 Apps Script 裡的檔案，按儲存。
2. 立刻選函式 `pauseReminderTriggers`，按執行。

成功：執行記錄出現「已暫停」，並且寫「沒有建立新觸發」。

這一步只刪本系統的 `sendReminders` 與 `sendMonthlySummary`。其他專案的觸發會留著。暫停之後，遷移過程不會再被舊的一三五或新的一四六觸發送出 LINE。

出錯：若執行記錄沒有這句，不要部署網頁應用程式。再執行一次 `pauseReminderTriggers`。不要改執行 `setupTriggers`。

## 4. 檢查必填設定，仍不發送

選函式 `releaseReadiness`，按執行。

成功：記錄裡的 JSON 是 `ok: true`、`missingProperties` 為空、`reminderTriggers` 為 0、`groupPushEnabled` 為 false、`apiVersion` 為 `2026-11-release-2`。這個函式不讀名單、不發訊。

出錯：`ok: false` 時，只補 `missingProperties` 列出的屬性，再跑一次。在變成 `ok: true` 之前不要部署。

## 5. 部署同一個 /exec，先確認後端

1. 「部署 → 管理部署」。
2. 編輯已經在用的那個網頁應用程式，不要按「新增部署」。
3. 版本選「新版本」。執行身分仍是「我」，存取權仍是「所有人」。
4. 部署完成後，網址必須跟原來的 `/exec` 完全相同。

成功：用瀏覽器打開這個網址，看到的 JSON 含有 `"apiVersion":"2026-11-release-2"`，以及 `observer`、`tier-B`、`pending-not-D`、`schedule-mon-thu-sat-09`。

出錯：

- 網址變了：你新增了一個部署。不要把新網址寫進前端。刪除或停用那個新部署，回到舊的那筆改版。
- JSON 沒有 `apiVersion`：線上仍是舊版。在管理部署裡改選剛剛建立的新版本，再重新整理 `/exec`。
- 這一步通過之前，不要更換 GitHub Pages。

舊的小頁面這時仍可暫時使用。新後端仍接受舊畫面的認領與回訪。新畫面需要的 B、待核實、觀察者，要等第 8 步才換。

## 6. 用最新正式表做遷移 dry-run

1. 確認第 3 步的觸發仍然是暫停的。
2. 設定 `SOURCE_26_SHEET_ID`、`SOURCE_27_SHEET_ID`。不要把這兩個 ID 寫進 Git。
3. 選函式 `migrationDryRun`，按執行。

成功：`wrote` 是 false，`ok` 是 true。記錄有這次的 `fingerprint`、`liveClaims`、`liveVisits`。同名的人仍然分開。2-6 與 2-7 是待核實，不是 D。

對照 2026-11-07 的參考值時：

- 認領多於 139，或回訪多於 22：這是後來新增的正式資料，必須保留。不是錯誤。
- 少於 139 或 22：先不要確認。核對是不是開錯試算表，或有人取消了認領。程式不會把 139／22 寫回去。
- 名單結構不是 A35／B16／C37／D599、2-6 的 248、2-7 的 71、候選 1006、同名組 14：`ok` 會是 false。不要確認。

把這次的 `fingerprint` 複製到指令碼屬性 `MIGRATION_FINGERPRINT`。不要複製整份名單。不要用更早一次 dry-run 的指紋。

出錯：`wrote` 必須仍是 false。正式表沒有被這一步修改。修正來源表或屬性後，重新 dry-run，產生新指紋。

## 7. 確認遷移

1. 把 `MIGRATION_CONFIRM` 設為 `確認遷移`。
2. 選函式 `migrationConfirm`，只執行一次。

成功：回傳 `wrote: true`，並有 `backupId`。接著人工看試算表：

- A／C／D 的「我要認領」與確認前相同，只多了「穩定ID」。
- 回訪筆數等於第 6 步的 `liveVisits`。
- 「資料鍵」變成穩定 ID，「舊資料鍵」仍是原來的 `分頁|列號`。
- 有「B 穩定」與「待核實」。待核實的出席狀態不是 D。
- 同名的人仍是不同列。

出錯：

- 回傳指紋不同、`wrote: false`：正式表在 dry-run 之後又有變動。不要重試同一個指紋。再跑第 6 步。
- 已寫入但內容看起來不對：把 `RESTORE_BACKUP_ID` 設成回傳的 `backupId`，先執行 `restoreDryRun`。成功是 `wrote: false` 並列出要回復的分頁。確認要蓋回時，把 `RESTORE_CONFIRM` 設為 `確認回復`，執行 `restoreConfirm`。成功是 `wrote: true`，認領欄與回訪鍵回到備份內容。
- 沒有 `backupId` 就不要自己刪分頁。用第 2 步的試算表複本核對。

## 8. 後端確認後才換前端

1. 用這次交付的 `index.html` 更換 GitHub Pages 上的檔案。LIFF ID 與 `/exec` 網址都不要改。
2. 用 LINE 打開原來的小頁面。

成功：看得到 A／B／C／D／待核實，以及「只查看（觀察者模式）」。用一個既有帳號看得到自己原來的認領。不要在這一步發測試推播。

出錯：若畫面寫「後端還沒換成這個版本」，表示 Pages 已換、`/exec` 仍是舊版。立刻把 Pages 換回第 2 步保存的 `index.html.舊版`，回到第 5 步。不要合併 Pull Request 來「修」這件事；若儲存庫的 Pages 是從 `main` 自動發佈，合併 PR 會直接換成新前端。

## 9. 最後才恢復排程

前端與遷移都確認之後，才選 `setupTriggers` 執行一次。

成功：執行記錄寫每週一、四、六 09:00，以及每月 1 日 08:00，並說明 `nearMinute` 不保證準時 09:00。再執行 `releaseReadiness`，`reminderTriggers` 應為 4（三個每週加一個月報）。

這只表示觸發已建立。它不能證明到了週一 09:00 一定準時送到。Apps Script 只保證在該小時內接近 09 分。

出錯：若不想讓它在下一個週一、四或六送出，再執行 `pauseReminderTriggers`。成功時 `reminderTriggers` 回到 0。

群組推播維持關閉，直到另外決定把 `GROUP_PUSH_ENABLED` 設為 `true`。沒有設之前，個人提醒會在那三天送出，兩個群組不會。

## 10. 陳永傑先不要移轉

這次上線不要設定 `REPAIR_CONFIRM`，不要執行 `adminBindingConfirm`。

若只想再看一次，可執行 `adminBindingDryRun`。成功是 `wrote: false`。顯示名稱、認領筆數或回訪筆數若已和先前看到的不同，就停，不要確認。dry-run 不會解除綁定，也不會刪認領。

## 還沒在正式環境驗證的部分

本機測試通過，不代表正式表已經跑過。尚未在正式環境做的有：

- 沒有開啟正式試算表，所以沒有核對今天的實際認領與回訪筆數。
- 沒有在正式 Apps Script 執行暫停、部署、dry-run 或回復。
- 沒有發送 LINE，也沒有取得權杖。
- 同名 14 組的實際姓名沒有重新點算；程式只保證同名不會自動合併。
- 1006 筆候選沒有在這次作業裡從正式表重算。
- 週一、四、六 09:00 的真實觸發時刻無法由單一頁面或本機測試證明。
- 這個 GitHub 儲存庫目前沒有 CI 檢查。PR 可以合併，但現在合併會有把新前端早於後端公開的風險。
